## Why this stage existed

Stage 3 showed that "far from average" confuses harmless slow spikes with real attacks. But our faults have a direction: a skipped loop only ever makes a stage shorter, and a spike only ever makes one longer. So we stopped asking "is this boot strange?" and asked "is any stage suspiciously short?"

## The floor rule

For each of the 21 sub-stages (checkpoints 1 to 7, three each):

1. Take the median of that sub-stage over the clean calibration boots. The median is the middle value, so spikes barely move it.
2. Multiply by 0.45. That is the **floor**.
3. At boot time, if any sub-stage comes in under its floor, alarm.

The whole detector is one loop in [floor_detector.c:7-13](../src/floor_detector.c#L7): return 1 if any `sub[i] < FLOOR_TABLE[cp][i]`. The table is generated by `calibrate_floor.py` into `floor_table.h`. The code is 92 bytes and the table 48 bytes, 140 in total, with no multiplies or square roots.

## The same boots as before, through both detectors

CP3 floor for `sub_a`, `sub_b`, `sub_c` is 310, 300, 234:

| Boot | Timings | Floor says |
|---|---|---|
| Clean, ordinary | 783, 860, 656 | continue |
| Clean, spiked (boot 203) | 764, **3,790**, 579 | continue |
| Clean, spiked (boot 280) | 862, 850, **3,588** | continue |
| Attack | 583, **93**, 542 | **halt** (93 is under 300) |

The spiked boots that fooled Mahalanobis are invisible to the floor, because they only go up. The attack is caught clearly: its `sub_b` is 93 against a floor of 300.

## Does it hold up?

**Held-out, offline.** Fit on half the clean boots, test on the other half, four splits. At F = 0.45 and 0.5:

| | Floor |
|---|---|
| False alarms on clean boots, CP1 to CP7 | 0 |
| Alarms at checkpoints a fault did not touch | 0 |
| Worst-split detection of the five skipped-loop faults | 298 to 299 of 300 |

**On fresh boots, in the firmware.** 300 new boots of each of 7 builds, on the final binary. The Python mirror agreed with the firmware on all 2,100 boots.

| | Floor | Mahalanobis (CP3) |
|---|---:|---:|
| Clean false alarms | 0 / 300 (95% upper bound 1.3%) | 17 / 300 (5.7%) |
| Attack | 299 / 300 | 300 / 300 |
| FT-1 | 299 / 300 | not watched |
| FT-2 | 300 / 300 | 300 / 300 |
| FT-3 | 298 / 300 | not watched |
| FT-4 | 300 / 300 | 300 / 300 |
| FT-5 (extra work) | **0 / 300** | 300 / 300 |

**On the real halting builds.** Same 300 boots, but without the "keep going" mode, so the boot truly stops. Clean: 0 halted, 293 completed, 7 completed after a warning. Attack, FT-1, FT-2, FT-4: 300 of 300 halted. FT-3: 299 of 300. FT-5: none halted, all 300 warned.

The faulted boots the floor missed were not fully skipped loops. In the attack build, boot 177 had `sub_b` = 978, a normal size. In the FT-1 build, boot 108 had `sub_b` = 355, above its floor of 305. A host pause probably inflated the shrunken sub-stage. That is a guess, since the data cannot tell us the cause.

## Choosing F = 0.45

| F | What happens (held-out) |
|---|---|
| Below 0.30 | Faults slip through. Worst fault missed: 1.7% at 0.30, 36% at 0.25, 94% at 0.20 |
| 0.30 to 0.50 | No false alarms, nothing alarms at the wrong checkpoint |
| 0.55 and above | Healthy checkpoints in other builds start alarming: 1% at 0.55, 5% at 0.60 |

The lowest healthy sub-stage in the clean data is 0.68 of its median, and an untouched sub-stage in a fault build reached 0.51. So 0.45 sits inside the usable window, a little under the 0.51 line. **Be honest about this:** we chose 0.45 after seeing the fault data. The fresh boots check the calibration, not the choice of rule.

## The tiered response

| | Floor | Mahalanobis |
|---|---|---|
| Where | CP1 to CP7 | CP3 only |
| False alarms on clean boots | 0 of 300 | 17 of 300 |
| Sees extra-work faults (FT-5) | no | yes |
| **Response** | **halt the boot** | **print a warning, continue** |

Halting on Mahalanobis would stop about 1 good boot in 18. The floor has no measured false alarms, so stopping is safe. The code is [report_alarm](../src/main.c#L368): a `halt` flag chooses between "WARNING ONLY - boot continues" and `while(1)`. Mahalanobis is kept because it is the only thing that sees FT-5.

## The timer guard

Under heavy host load, QEMU's timer can wrap or stall and report zeros, which a floor would read as a skipped loop. In an earlier load test of 60 boots, 28 had no usable readings, and (from a note made at the time, with no saved raw data) the floor alarmed on 27 of those 60. So [timer_ok](../src/main.c#L352) checks that elapsed time rises, stays under the 24-bit maximum, and covers the three sub-stages. If not, both detectors skip that checkpoint and print `TIMER_INVALID`.

Two limits: it fails open (a fault that also corrupted the timer would pass), and it never fired in any validation boot, so the skip path is untested in firmware (ISSUE-019).

## What the floor cannot do

- **Longer stages.** FT-5 is invisible to it (0 of 300). Only the Mahalanobis warning sees it.
- **Mild faults.** The floor needs roughly a 60% reduction to be reliable. In the synthetic sweep on `sub_b` alone it caught 0% at a 30% cut, 26% at 40%, 33% at 50% and 96% at 60%. QEMU cannot make partial skips, so this curve is simulated.
- **Faults we did not inject.** Faults sat only at CP1, CP3 and CP7. Checkpoints 2, 4, 5 and 6 were tested only by clean boots.
- **Build changes.** Every new binary needs its floor table regenerated.

## The whole story in five lines

1. Python detector on one checkpoint: worked on fake faults (Stage 1).
2. Ported to C with fixed-point maths, three bugs fixed: worked on one real fault, 14 of 1000 false alarms (Stage 2).
3. Widened to 8 checkpoints and 6 faults: Mahalanobis fell apart because of timing spikes (Stage 3).
4. Switched to a one-sided floor: zero false alarms, 298 to 300 of 300 detections, 140 bytes (Stage 4).
5. Kept Mahalanobis as a warning-only second opinion, because it sees what the floor cannot.
